## Real gaps (by priority)

### GAP-1 · HIGH —— Re-verified: a real bug (initial misjudgment overturned, genuine gap, see R-13)
> ⚠️ **Second re-verification (2026-10-13 follow-up, codebuddy tested against a real DB, overturning
> the main agent's initial misjudgment)**:
> The main agent's initial version misjudged GAP-1 as a false positive (based on the **unverified**
> assumption that "TimescaleDB 2.x continuous aggregates default to `materialized_only=false`").
> codebuddy installed the **real** `timescaledb 2.13.1` (same version as `infra/docker-compose.yml:45`)
> + ran `infra/init.sql` (rc=0), and empirically established:
> - `_timescaledb_catalog.continuous_agg.materialized_only`: `robot_history_10s = t`,
>   `robot_history_1h = t`, `robot_status_10s = t` (**all three true**);
>   `pg_get_viewdef('robot_history_1h')` is a **purely materialized table** (no `UNION ALL` live segment);
> - After loading `[now-30min, now]`, `SELECT count(*) FROM robot_history_1h WHERE bucket >= now()-90min`
>   returns **0** (live segment not backfilled); after
>   `ALTER … SET (timescaledb.materialized_only=false)` the same query returns **1** → the difference
>   is entirely determined by `materialized_only`;
> - **Root cause (two upstream pieces of evidence)**: `timescaledb 2.13.1` source
>   `src/ts_catalog/continuous_agg.c:58-62` defaults `materialized_only = true`; the upstream
>   regression test `tsl/test/expected/cagg_union_view-15.out` corroborates (`=false`→UNION live view;
>   `=true`→`(0 rows)`).
> ⇒ **GAP-1 is a real bug**: the two `/history` paths (10s + 1h) lose their right-end live segment
> (1h / 10s hole) because the cagg `materialized_only=true`.
> **Fix (R-13)**: explicitly `ALTER … SET (timescaledb.materialized_only=false)` on `robot_history_1h`
> + `robot_history_10s` to enable live aggregation, plus a real-DB regression test.
> `robot_status_10s` (dashboard's latest state, 1min hole) is a sibling of the same kind, left for a
> separate later evaluation.

### GAP-2 · MED —— Alert engine `consume()` has no Redis disconnect supervision (process-level single point)
- Evidence: `amain()` uses `asyncio.gather(consume(), ticker(), escalation_loop())`
  (`alert_engine/app/main.py:312`); `consume()`'s `async for msg in pubsub.listen()` (`:230`)
  **only try/excepts `json.JSONDecodeError`** (`:233`); a dropped Redis connection throws
  `ConnectionError` that escapes the loop → `gather` propagates the exception → the entire engine
  coroutine tree fails (the container restarts externally, but in-process alert consumption stops
  permanently).
- Consequence: a Redis blip / network jitter silently stops alerts (the ticker offline-detection
  still runs, but streaming alerts are all lost).
- Fix direction: wrap the loop in try/except + backoff reconnect; or package `consume` as a
  self-restarting task (`while True: try: ... except: await asyncio.sleep(...); continue`).

### GAP-3 · MED —— Notification delivery failures have no metric / no retry (observability blind spot)
- Evidence: `main.py:217` comment explicitly says "notification failure is only logged inside the
  notifier, does not affect the main chain"; `webhook.py:95/102/115` throws `RuntimeError`/
  `log.exception` then drops it, with no counter.
- Consequence: when the webhook is misconfigured / the WeCom API is rate-limited, alerts **are
  persisted but notifications are silently lost**, and there is no `robot_alert_notify_failed_total`
  metric to alert on → nobody knows.
- Fix direction: add a `robot_alert_notify_failed_total{reason}` metric + optional exponential-backoff
  retry (failed alerts re-enqueue, without blocking the main chain).

### GAP-4 · LOW —— Backend has no CORS / rate-limit config
- Evidence: `backend_ingestion/app/main.py` grep for `cors|rate.?limit|throttle` found nothing
  (only JWT auth).
- Consequence: if frontend and backend are deployed cross-origin, WS/REST will be blocked by browser
  CORS; no rate limiting (usually acceptable on an internal trusted network).
- Fix direction: add `CORSMiddleware` per deployment topology + optional slow-client/endpoint limiting.

### GAP-5 · LOW —— `init.sql` retention/compression policy lacks `if_not_exists`
- Evidence: `init.sql:277-279` comment notes `add_retention_policy`/`add_compression_policy` do not
  expose `if_not_exists`; current `PERFORM add_retention_policy(...)` (`:316/:342`) errors on re-run.
- Consequence: re-running `init.sql` after policies are built fails, hindering DR rebuild / environment reset.
- Fix direction: wrap with `DO $$ … IF NOT EXISTS (SELECT … policy_retention) …` (same shape as the
  existing `policy_compression` check, `:301-313`).
